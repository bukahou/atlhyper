# AIOps 拓扑归并：沿依赖链的连锁故障归为一组、指出源头

> 状态：**已裁决，实施中**（2026-11-15 用户：D1–D6「都按推荐做」）。来源：事件通知项目裁决时「完整的拓扑归并另行立项」。
> 前置：事件已按主体收敛（同一工作负载的 Pod 归一个事件），见 `incident-notification-design.md` 功能零。

## 背景

### 现在会发生什么

事件以**主体**为单位：工作负载（Deployment / StatefulSet / DaemonSet / Job / CronJob）、Service、Node、Ingress 各自是主体。
风险沿依赖图传播（`risk/propagation.go`）：`R_final = max(R_weighted, 0.6 × R_weighted + 0.4 × 依赖的平均 R_final)`，
依赖图的边是 `Pod → Node`（runs_on）、`Service → Pod`（selects）、`Ingress → Service`（routes_to）、`Service → Service`（calls，来自链路）。

于是**一次故障会在依赖链上开出好几个事件**：

| 场景 | 现在开出的事件 |
|---|---|
| 一个 Deployment 的 Pod 全部崩溃，它有一个 Service | Deployment 一个（升级、通知），Service 一个（传播来的 0.36，停在警告）——**几乎每个带 Service 的工作负载都会这样** |
| 数据库 StatefulSet 挂了，两个服务经链路调用它 | 数据库 StatefulSet、数据库 Service、两个调用方 Service，各一个；调用方若错误率上升还会各自升级、各自通知 |
| 一个节点内存压力 | 节点一个；节点上每个工作负载的 Pod 都分到传播风险，叠加自身 NotReady 等信号，**每个工作负载各一个事件、各一条通知**（通知风暴） |

看事件列表的人要自己把它们串起来，看通知的人会同时收到一串。

### 现有可以利用的

- 依赖图（实体级，按集群），带正向 / 反向邻接表
- 风险传播时已经算出**传播路径**（`PropagationPath`：从哪个依赖传到哪个实体、贡献多少）
- 每个实体有本地风险 `RLocal` 与信号 `Signals`（传播来的风险没有本地信号）
- 主体 ↔ 成员实体的映射（`subject.ResolveSubjects`）
- 通知管道已有「抑制」机制（集群离线时抑制该集群的告警），可以扩展

## 目标

1. 依赖链上同一次故障的事件**归为一组**，组里有一个**源头事件**，其余是**受影响事件**
2. 通知默认只发源头，消息里列出受影响的对象；源头恢复了而受影响的还没恢复，再单独通知它们
3. 事件列表按组折叠显示；详情页给出「影响范围」与归组的依据（依赖路径）
4. 不改状态机与事件的基本形态；归组判断错了能看出来为什么

不在本期：跨集群归并；人工「解除关联」（并入后续的「反馈回路」项目）；基于历史的相关性学习。

## 待用户裁决的决策点

### D1 归组的形态

| 选项 | 做法 | 影响 |
|---|---|---|
| A. 关联 + 抑制（推荐） | 每个主体照旧各开一个事件；另记一张「谁归到谁」的关联表，受影响事件指向源头事件 | 状态机、事件表、通知管道的现有逻辑都不动，只加一层关联；归错了只影响关联、不影响事件本身；与 Alertmanager 的抑制规则、PagerDuty 的关联事件同一思路 |
| B. 真合并成一个事件 | 一个事件里装多个主体 | 状态机现在按主体一个条目，要改成按组；各主体各自恢复、复发的语义要重新定义；改动大，归错了难以拆开 |

### D2 什么情况下归为一组（判定规则）

两个同时活跃（警告 / 事件中）的事件 X、Y，满足以下全部条件时，Y 归到 X 之下（X 是 Y 的上游）：

1. **依赖可达**：从 Y 的任一成员实体沿依赖方向（依赖图的正向边）走不超过 **4 步**，能到达 X 的某个成员实体
2. **时间先后**：X 的开始时刻不晚于 Y 的开始时刻 + **2 分钟**（容忍采集与判定的先后误差）
3. **X 仍活跃**：X 处于警告或事件中

| 选项 | 区别 | 影响 |
|---|---|---|
| a. 只看依赖可达 | 不看时间 | 两个碰巧同时出问题、但并无因果的上下游会被归到一起 |
| b. 依赖可达 + 时间先后（推荐） | 如上 | 主流做法（拓扑 + 时间窗）；误归的主要来源被时间先后排掉 |
| c. 再加「Y 没有本地信号才归」 | 只归纯传播来的 | 太严：调用方因数据库挂了而错误率上升，是它自己的本地信号，但根因在上游，会被漏掉 |

### D3 源头怎么定

一组里**没有活跃上游**的事件是源头；如果有多个（链上有两个独立起点），取**开始最早**的；仍相同取风险高的。
链式情况（A ← B ← C）全部挂到最上游 A，不做多层嵌套。

### D4 通知怎么发

| 选项 | 做法 | 影响 |
|---|---|---|
| a. 只发源头，消息里列受影响对象（推荐） | 受影响事件的告警被源头抑制；源头的消息带「影响 N 个对象：…」 | 一次故障一条通知；源头恢复而受影响者仍在时，抑制解除，它们按正常规则通知 |
| b. 全部照发 | 不抑制，只在消息里标注「源头：…」 | 不漏任何一条，但风暴照旧 |
| c. 源头立即发，受影响者汇总成一条延迟摘要 | | 多一种消息形态，复杂度高，收益不明显 |

### D5 界面

- 事件列表：源头一行，右侧「关联 N 个」可展开；受影响事件默认折叠在源头下面（筛选可切换「全部平铺」）
- 详情页（源头）：新增「影响范围」块，列受影响事件与各自的依赖路径（如 `api(Service) → calls → db(Service) → selects → db-0(Pod)`）
- 详情页（受影响）：结论块下方一行「源头：<主体> · 经 <路径>」，可跳转

### D6 归错了怎么办

| 选项 | 做法 | 影响 |
|---|---|---|
| a. 本期只自动，显示依据（推荐） | 详情页写明归组依据（路径 + 先后时间）；归错的情况记下来，作为「反馈回路」项目的输入 | 实现小；判断透明，错了能看出来为什么 |
| b. 本期加「解除关联」按钮 | 管理员手动拆开，之后不再自动归回 | 需要「人工覆盖」的持久化与权限，属于反馈回路的范围 |

## 裁决记录（2026-11-15）

| 决策 | 裁定 |
|---|---|
| D1 归组形态 | A：关联 + 抑制（事件照旧各自存在，另记归属关系） |
| D2 判定规则 | b：依赖 4 步内可达 + 上游不晚于下游 2 分钟 + 上游仍活跃 |
| D3 源头 | a：最上游（多个起点取最早，再取风险高）；链式全部挂到最上游，不嵌套 |
| D4 通知 | a：只发源头，消息带影响范围；源头先恢复则下游解除抑制、按正常规则通知 |
| D5 界面 | a：列表折叠（可切平铺）；源头详情「影响范围」，下游详情「源头：…经…」 |
| D6 归错 | a：本期只自动，详情页写明依据；人工解除并入「反馈回路」项目 |

## 实施方案

### 数据

新表 `aiops_incident_links`（`CREATE TABLE IF NOT EXISTS`，**不用清库**）：

| 列 | 说明 |
|---|---|
| `incident_id` | 受影响事件（主键） |
| `root_incident_id` | 源头事件 |
| `path` | 依赖路径（JSON：实体键与边类型的序列），作为归组依据展示 |
| `linked_at` / `unlinked_at` | 归入 / 解除的时刻；源头恢复或受影响事件结束时写 `unlinked_at` |

### 判定时机与位置

- 引擎每轮评估之后（与本轮证据记录同一处），对本集群活跃事件跑一次归组：输入「活跃事件 + 主体成员 + 依赖图」，输出「受影响 → 源头 + 路径」。纯函数，单测覆盖
- 关联变化（新归入 / 换源头 / 解除）作为一种新的事件变化发布，通知模块据此调整抑制

### 通知

- 告警对象加一个「被谁抑制」的标记；管道的抑制判断在「集群离线」之外加一条「源头事件活跃」
- 源头告警的消息里加「影响范围：N 个对象」与前几个对象名
- 解除抑制（源头先恢复）时，仍在持续的受影响告警按「触发」发一次（与「静默到期」同一规则）

### 接口（契约）

**事件列表** `GET /api/v2/aiops/incidents`：每条事件新增

```json
{
  "...": "原有字段",
  "rootIncidentId": "inc-123",          // 受影响事件：归到的源头事件号；不是受影响事件时为空串
  "linkedCount": 2,                     // 源头事件：当前归到它下面的受影响事件数；否则 0
  "impacted": [                         // 只在 grouped=true 且本条是源头时给出，否则为空数组
    { "incidentId": "inc-124", "subject": "shop/service/api", "subjectType": "service",
      "state": "warning", "severity": "medium" }
  ]
}
```

查询参数 `grouped=true`：受影响事件（`rootIncidentId` 非空）不单独出现，折叠在源头的 `impacted` 里；`total` 按折叠后的条数算。
不传或 `grouped=false` 时照旧平铺。

**事件详情** `GET /api/v2/aiops/incidents/{id}`：新增

```json
{
  "...": "原有字段",
  "root": {                             // 本事件归到某个源头时给出，否则 null
    "incidentId": "inc-123", "subject": "shop/statefulset/db", "subjectType": "statefulset",
    "state": "incident", "severity": "critical",
    "path": [                           // 归组依据：从本事件的成员沿依赖走到源头的成员
      { "entityKey": "shop/service/api", "edge": "" },
      { "entityKey": "shop/service/db",  "edge": "calls" },
      { "entityKey": "shop/pod/db-0",    "edge": "selects" }
    ],
    "linkedAt": "2026-11-15T07:00:00Z"
  },
  "impacted": [                         // 本事件是源头时：归到它下面的受影响事件；否则空数组
    { "incidentId": "inc-124", "subject": "shop/service/api", "subjectType": "service",
      "state": "warning", "severity": "medium", "path": [ "...同上，从受影响事件走到本事件..." ],
      "linkedAt": "..." }
  ]
}
```

- `edge` 取值：`""`（起点）/ `calls` / `selects` / `runs_on` / `routes_to`，前端按 i18n 显示（调用 / 选中 / 运行在 / 路由到）
- 只给当前有效的关联（源头恢复或受影响事件结束后，关联解除，不再出现）
- 风险与结论的文字仍由前端按 i18n 渲染

### 验证

dev 上用崩溃测试应用加一个 Service：应只收到 Deployment 一条通知，Service 的事件归在它下面；
删掉应用后两者先后恢复，Service 不单独发通知。节点类场景不在 dev 上人为制造（会影响整个节点上的服务），只靠单测覆盖。
